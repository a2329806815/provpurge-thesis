# ProvPurge 创新点可行性核查

> 评估对象：《ProvPurge 创新点定稿与代码实现方案》与《ProvPurge 方法规格书》。  
> 评估边界：只做可行性评估，不写代码、不跑实验、不修改规格书。  
> 现实约束：一名硕士生独立完成；5×RTX 3090 24GB；本地推理；无大额 API 预算；结果必须来自真实代码与真实运行；目标为 CCF 主会长文；开发和实验均须按阶段向 Joseph 汇报并获准。

## 0. 先给结论

**完整定稿版不是不能做，而是不能按“所有贡献全量展开、所有基线与消融全量重跑”的方式一次做完。** 以一名全职投入的研究生计，共享底座加主贡献约需 **12–20 人周**；再把 A 做成可信的因果证据、B 做完整双语义分析、C1 与 C2 都全量展开，项目很容易膨胀到 **24–34 人周**，还没有充分计入论文写作、导师修改、基线仓库故障和正式实验失败重跑。

最合理的收缩方式是：

1. 先做主贡献的最小完整闭环：句级来源、闭包与实体扩展、三层硬删、探针门、记分卡回执、缺席检查。
2. B 的语义分支随主系统一起实现，但先只作为方法语义和 F4 描述性分析，不单独承担强结论。
3. 在正式主跑前预留 C1：门控集冻结后生成并密封留出探针，删除前做阳性对照，删除后只运行一次留出集。
4. C2 先压缩为“四档验证器对照 + 行未真删 + 删后写回”两类关键假接受攻击；不要一开始就做全量预算曲线。
5. A 先保留为安全规则和描述性分层；只有主贡献与 C1 站稳后，才做来源边/锚损坏注入实验，把它升级为因果证据。

**若只能保住“主贡献 + 一条”，保 C1。** 理由是 C1 直接防守审稿人对主贡献最致命的质疑——系统反复针对同一组门控探针扩候选，门控全过可能只是“刷题”；B 可以退为方法细节，C2 的缺席检查与写回检出可以并入主贡献的回执验证，A 可以退为安全规则。三者都不必为了“保 C1”而从系统里删除。

### 0.1 总判定速览

| 条目 | 判定 | 一句话原因 |
|---|---|---|
| 贡献一：探针门控硬删除事务 | **有条件可做** | 工程闭环成立，但逐轮写入、严格 RPR、Qwen 抽取质量和总运行量决定成败 |
| 贡献二 A：不完整来源闭包 | **高风险** | 机制能写，官方 BEMULA 却没有可控的“来源不完备”处理变量与金标，因果证据须自建注入实验 |
| 贡献三 B：F4 源—结论双语义 | **有条件可做** | 实现增量不大，但 BEMULA 未提供语义金标且 F4 只有 13 条请求，只能做小样本附加分析 |
| 贡献四 C1：留出探针泛化缺口 | **有条件可做** | 一人可完成流程版密封与校准，但有效样本受 50 个实例聚类限制，只能可信地识别较大缺口 |
| 贡献四 C2：回执可验证性评测 | **有条件可做** | 限定版工程上最稳；全量重验、独立验证器和完整攻击矩阵会迅速扩大范围 |
| 贡献四 C1+C2 全量合并版 | **高风险** | 两套证据链叠加后工作量和统计/威胁模型复杂度过高；C1 为纲、C2 压缩版才可控 |
| LoRA 定位决策 | **有条件可做（仅可选消融）** | 默认不做是对的；只有试跑归因证明触发识别是首要瓶颈时才值得花 1.5–3.5 人周 |

## 1. BEMULA full 的规模与成本模型

### 1.1 已核实的规模事实

以下数字来自方法规格书、BEMULA 论文/仓库既有核查报告，以及对本地仓库 `data/full` 文件的静态计数；不是实验结果。

| 项目 | 数量 |
|---|---:|
| 实例 | 50 |
| forget 版 sessions / turns | 746 / 36,900 |
| control 版 sessions / turns | 746 / 36,900 |
| 两版合计 sessions / turns | 1,492 / 73,800 |
| 遗忘/更新请求 | 135 |
| 请求类型 | F1 32、F2 23、F3 26、F4 13、F5 20、F6 21 |
| 官方题目记录 | 1,742 |
| relearning 附加 context turns | 428 |
| 适配器实际 observe 的 turns | 73,800 + 428 = **74,228** |

官方 runner 的两遍协议不是把 1,742 题简单各问一遍：

| 协议部分 | adapter.query 次数 | 官方 LLM judge 次数 |
|---|---:|---:|
| control：Retention 224 + Preservation 150 + Attack 1,030 | 1,404 | 1,396 |
| forget：Efficacy 224 + Preservation 150 + Attack 1,030 + Relearning 114 | 1,518 | 1,499 |
| 合计 | **2,922** | **2,895** |

其余 27 条记录为 exact grading，不需要 LLM judge。judge 温度为 0；`probe_writeback=false`；默认 agent 模型口径为 `deepseek-v4-flash`，但 ProvPurge 规格已定为本地 Qwen3-32B 级、具体版本待试跑定版。BEMULA 没有官方成本或时长数据，因此本文只算调用量和 token 下限，不编造美元成本和完成时间。

### 1.2 真正的成本大头不是官方问答，而是 ProvPurge 写入路径

BEMULA 对话平均约 84.8K tokens/实例/版本。两版 50 个实例仅“把对话完整读一遍”的文本量就约为：

\[
50 \times 84.8K \times 2 \approx 8.48M\ tokens
\]

这只是语料本体下限，不含系统提示词、检索上下文、抽取输出、探针上下文、judge rubric 和重复上下文。

ProvPurge 的写入实现有三种量级完全不同的形态：

| 写入形态 | LLM 调用量 | 说明 |
|---|---:|---|
| 按 session 批处理抽取 | 约 1,492 次主会话调用，另加 relearning 小上下文处理 | 单次上下文长，但调用数低；必须在 session 内按轮次顺序模拟触发与状态变化 |
| 每 turn 一次合并调用 | **74,228 次** | 在同一次调用中做触发判断、事实抽取和来源定位；是逐轮实现的较优情形 |
| 每 turn 抽取 + 对 user turn 再做触发识别 | 74,228 + 37,114 = **111,342 次** | 37,114 来自两版 user turns 36,900 + relearning user turns 214 |
| 摘要若每 session 单独生成 | 再加 **1,492 次** | 若与 session 批抽取合并，可避免重复加这一项 |

因此，**逐轮实现的一次 ProvPurge full 评测，写入侧就是 7.4 万至 11.1 万次 LLM 调用**。如果每次抽取还把当前 session 的完整历史重复塞入 prompt，token 量会从 8.48M 的线性下限膨胀为多倍；实现时必须采用增量上下文、当前 turn 加有限状态摘要，禁止“每轮重放整段会话”。

### 1.3 探针门一轮的调用量

按规格书第 7.2 节的最低配置粗算，并明确假设如下：

- 每个请求至少 4 道目标探针：原生问答、residual 直喂、推导/多跳、陈旧前提/攻击型。
- F4 每个请求另加至少 2 道再推导探针。
- 兄弟保全探针数量规格未冻结；下表以每请求 3 道为规划情景，公式保留变量 \(n_s\)。

目标探针数：

\[
(135-13)\times4 + 13\times6 = 566
\]

每轮探针回答生成数：

\[
Q_{round}=566+135n_s
\]

| 兄弟探针/请求 \(n_s\) | 每轮回答生成 | 每轮 judge 规划量 |
|---:|---:|---:|
| 1 | 701 | 135–701 |
| 3 | **971** | **135–971** |
| 5 | 1,241 | 135–1,241 |

judge 下限 135 的含义是“按请求批量裁判”：一次 judge 调用结构化返回该请求全部探针 verdict。上限是逐探针 judge。批量裁判减少调用数，但不按比例减少 judge token，且更容易出现一项解析失败污染整批结果；试跑必须实测可靠性，不能只为省调用而默认批量。

若所有请求都跑满 \(R\) 轮，回答生成上限为：

| 最大轮次 \(R\) | 探针回答生成上限 | judge 上限（逐探针） |
|---:|---:|---:|
| 1 | 971 | 971 |
| 2 | 1,942 | 1,942 |
| 3 | **2,913** | **2,913** |
| 5 | 4,855 | 4,855 |

实际总量取决于有多少请求进入下一轮。若第 1 轮后只有比例 \(f_1\) 进入第 2 轮、第 2 轮后只有 \(f_2\) 进入第 3 轮，则回答量约为 \(971(1+f_1+f_1f_2)\)，不是必然跑满上限。

还有一个敏感性风险：上表按“每请求”生成探针。如果实现时改成“每个目标事实”生成 4 道探针，目标探针将从 566 增至约 1,076，整轮总量约放大 1.5 倍。规格当前口径是每请求至少四类各一题，实施时不得无意改成每事实一套。

### 1.4 一次完整 ProvPurge full 评测的规划总量

以逐轮合并写入、每 session 单独摘要、\(n_s=3\)、所有请求跑满 3 轮的最坏规划为例：

| 组成 | LLM 调用 |
|---|---:|
| 写入 observe 处理 | 74,228 |
| session 摘要 | 1,492 |
| 官方 query | 2,922 |
| 官方 judge | 2,895 |
| 探针门回答，最多 3 轮 | 2,913 |
| 探针 judge，批量至逐项 | 405–2,913 |
| **合计** | **84,855–87,363** |

若触发识别与抽取分开，最多再加 37,114 次，总量约 **121,969–124,477** 次。若按 session 批处理抽取且摘要合并，调用数可降至约 **1.1 万–1.5 万次**，但这不等于 token 和时延同比例下降，因为每次调用要处理整段 session 并输出大量结构化事实。

C1 与 C2 的额外量：

- **C1**：删除前对 gate 与 holdout 两套目标探针做阳性对照，约 1,132 次回答；删除后只跑 holdout，约 566 次；合计新增 **1,698 次回答 + 405–1,698 次 judge**。前提是能在删除前内存快照上只读运行；若没有快照、必须第三次 ingest forget 版，还会再增加 36,900 turns 的写入处理。
- **C2**：若对全部 135 张回执各做一次完整探针复检，新增 **971 次回答 + 135–971 次 judge**。若只抽样 30 张回执，探针复检约 216 次回答，但论文主张必须相应改成“抽样验证评测”，不能写成每张回执都已独立复检。

### 1.5 项目级乘数比单次运行更危险

主贡献不是只跑一次 ProvPurge：

- 规格冻结了 5 项消融。若每项都从头 ingest，单是 5 个 ProvPurge 变体就可能再产生约 **42 万次**逐轮式 LLM 调用；这还没有算主跑、基线、C1/C2 和失败重跑。
- 基线侧仅官方 query 与 judge 的固定部分，7 个基线就至少有 20,454 次回答与 20,265 次 judge，另加各基线自己的写入、检索、更新和内部 LLM 调用。
- 因而项目级失控点不是探针门的 971 次/轮，而是**每个变体都重跑 7.4 万 turn 写入 + 重复官方评测**。

必须采用的成本控制：

1. **轮次上限先按 2 做试跑，3 只能由数据证明有增益后再定版。** 每请求同时设最大探针数、最大新增删除数、最大 token/调用预算；达到上限签 `failed`，不允许无限扩。
2. **中间轮允许早停，最终轮必须全跑。** 当前规格写的是每轮重跑全部探针；若要采用“中间轮首个目标泄漏即扩候选、最终轮完整记分”的优化，必须先修订规格并说明中间轮记分卡不完整，不能悄悄偏离规格。
3. **兄弟探针按受影响范围重跑。** 若新增删除集与某兄弟事实的来源、实体和检索上下文无交集，可复用其上一轮结果；有交集才重跑。该优化同样要写入规格/实现决议。
4. **judge 分层。** exact-target 与解析通道本地完成；语义 judge 对清晰拒答、清晰正确可批量，对边界项逐项。内部探针 judge 默认本地模型，外部 API 只保留给官方主评测或敏感性复核，不进入扩候选闭环。
5. **内存快照分支。** 同一实例 ingest 一次后保存只读快照，删除变体、A 注入和 C1 阳性对照从快照分支，避免每个消融重跑写入路径。快照必须包含三层存储、来源图、墓碑与版本信息，且分支间零串扰要有测试。
6. **基线收敛。** 主表优先保留 Full Context、Naive RAG、Mem0、LangMem 四类最有解释力的基线；其他基线只有在适配稳定且时间允许时再加。删减基线属于实验范围变更，须经 Joseph 确认并在论文中说明选择原则。
7. **先测吞吐再承诺 full。** 试跑必须按 short/medium/long/xlong 分桶报告每类调用的 tokens、延迟、失败率和每秒完成量。没有这些实测值，任何“几天能跑完”的承诺都不可信。

**特别问题①结论：探针门本身不会必然爆——它是每轮约千次、全量三轮约三千次回答；真正会爆的是无上限轮次、逐探针外部 judge、7.4 万 turn 逐轮写入，以及基线和消融的整套重复。把 \(R\le3\)、调用预算、本地 judge、快照复用和中间轮早停规则冻结后，成本可控；不冻结则不可接受。**

## 2. 贡献一（主贡献）：探针门控的硬删除事务

### 判定：有条件可做

### 实现难度与工作量估计

- 共享底座之外增量：**4–7 人周**。
- 含共享底座、主跑脚手架与第一轮结果分析：**12–20 人周**。
- 难度分布很不均匀：来源图遍历、闭包、greedy hitting set、哈希、Merkle/Ed25519 都是常规工程；难的是事实抽取与句级对齐、长会话状态管理、三层一致删除、待验状态隔离与回滚、摘要句外科改写、探针判定合同。

### 算力与成本风险

- 一次 full 的规划量见第 1.4 节：约 **8.5 万–12.4 万次**逐轮式 LLM 调用；session 批处理可把调用数降到约 1.1 万–1.5 万，但长上下文 token 仍高。
- BEMULA 论文中 Qwen3-32B-AWQ 一组系统 Score 最高仅 9.5，且作者指出抽取阶段是绑定约束。ProvPurge 规格只冻结“Qwen3-32B 级”，没有冻结 AWQ、BF16、具体版本和 judge 归属。若量化损伤抽取/裁判，主事务写得再对也会被底座拖死。
- BF16 32B 权重约 64GB，跨 3 张 24GB 卡仅权重就接近上限，还要给 KV cache、激活和运行时留空间；INT4 单卡可部署多副本，但量化误差可能伤抽取与 judge。试跑必须比较“抽取召回、触发识别、judge 一致率、吞吐”四项，不能只比速度。
- RPR 是全或无指标：一条请求自己的全部题和所在实例全部 preservation 题都对才通过。50 个实例、135 条请求下，系统即使平均题级正确率不低，RPR 仍可能很低。**工程可做不等于效果主张必然成立。**

### 依赖与前置条件

1. Joseph 先定版：骨干具体版本与量化方式、judge 本地/API、最大轮次、每请求成本上限、主表基线清单。
2. 写入抽取必须能稳定输出“事实—槽位—值—来源句序”；来源锚是 ProvPurge 自己生成的估计，不是 BEMULA 提供的金标。
3. 存储层必须支持事务快照/隔离区：探针在“已删待验”状态运行，失败还要回滚或剔除误删节点。若对象已物理抹除且没有待验副本，就无法回滚；若保留副本到提交后才清除，必须明确这段时间是逻辑隔离而非已完成硬删。
4. 探针判定合同先在自生成开发集上冻结，尤其是“等价表述恢复”的语义 judge、解析失败、部分泄漏和双通道冲突处理。
5. BEMULA 适配器必须只读 `speaker/text/timestamp`，不得使用 `linked_fact_ids`、`target_fact_ids` 等标注字段。

### 最可能翻车的点

1. **抽取与来源对齐先崩。** 长会话里同一事实多次提及、改写和跨 session 出现；抽取漏一条、句序对错一条，闭包就会漏。触发条件是 long/xlong 实例和 F2/F3/F5；表现是 RA 低、候选覆盖低、探针反复失败。
2. **待验删除与回滚语义自相矛盾。** 若先真删，兄弟探针失败后无法恢复误删；若靠隐藏/隔离实现待验，审稿人会问这是否仍是“读时藏匿”。触发条件是摘要改写失败、兄弟误伤或任一层删除失败。
3. **探针 judge 假阴性放行。** 模型用同义改写、拆分组件、只给可唯一反推的线索回答时，exact-target 通道不命中，语义 judge 又判未恢复，事务会错误提交。触发条件是攻击型、多跳和部分泄漏探针。
4. **探针 judge 假阳性造成死循环。** 无关记忆中的同名值、当前新值或合理拒答被判成旧值恢复，会不断扩候选、误伤兄弟事实，最后大量 `failed`。触发条件是 F6 同槽新旧值共存、F3 大范围删除和常见属性值。
5. **派生结论根本没有被存成节点。** F4 结论可能只在 query 时由源事实推出，而不是显式存在于事实/摘要层。此时闭包没有“结论节点”可删，只能靠防再推导墓碑和读路径拦截，主张必须区分“删存储结论”和“抑制再推导”。
6. **摘要重写误伤。** 只改目标句时衔接词、指代和时间线可能被生成模型顺手改动，逐句 diff 通过但语义已变，兄弟探针失败。触发条件是长摘要、多事实共句和代词指代密集的句子。

### 降级方案

- 保留三层硬删和探针提交语义，但把轮次上限压到 2；第 3 轮只对试跑证明“第 3 轮转化率足够高”的类型开启，且须先修订规格。
- 摘要层优先做“删目标句”而非整段重生成；只有目标句无法独立删除时才重生成，并把重生成失败率单独报告。
- 若 RPR 仍低，不改口成“解决 BEMULA”；主张降为“提出并验证一种删除事务语义，在 Score/FE/AR 与残余恢复上相对同底座基线改善，并用失败归因解释 RPR 的合取瓶颈”。若配对差小于规格的 5 个百分点，连“更优”也不能宣称，只能报告差异不明确。
- 若快照分支来不及，消融只保留最关键的三项：去探针门、去实体扩展、去来源图；池宽与读路径防御消融可降为附录或小节，但删减须经 Joseph 批准并同步实验清单。

## 3. 贡献二（A）：不完整来源下的闭包删除与拒提交规则

### 判定：高风险

这里的高风险不是说完备性检查写不出来，而是说**用官方 BEMULA 直接证明 A 的证据链不成立**。机制本身只需在主系统上增加检测、标记、拒提交与分层统计；但要证明“来源不完备确实造成风险、拒提交规则确实降低残余恢复”，必须有可控的不完备处理变量和独立标签。官方数据没有给 ProvPurge 这样的实验操纵。

### 实现难度与工作量估计

- 只做机制与描述性分层：**1–2 人周**增量。
- 做成可信的因果证据：**3–6 人周**增量，包含快照分支、注入控制器、剂量设计、配对运行、统计与失败分析。
- 若没有内存快照、每个注入剂量都要重新 ingest，工作量和运行量会再上浮，且多人周估计失效。

### 算力与成本风险

- 描述性版本几乎不增加模型调用，只增加检测与日志。
- 注入版本若设置 3 个损坏剂量、A 规则开/关两臂，并对每个剂量从头跑 forget 版，成本可接近数次额外 full；若从同一 ingest 快照分支，主要新增的是删除事务、探针和官方 forget 题评测，成本可控得多。
- 注入比例越高，`failed` 越多，探针轮次越容易跑满上限；成本不是随剂量线性增长，而会随失败事务的扩候选轮次陡增。

### 依赖与前置条件

1. 先有可复制的内存快照和事务分支，否则无法在同一初始状态下配对比较“拒提交开/关”。
2. 完备性阈值必须在自生成开发集上冻结，不能看 full 结果后调到最有利的触发率。
3. 注入控制器必须位于被测系统之外，只操纵 ProvPurge 的内部来源图副本；系统运行时不能读取 BEMULA 标注来决定标记或删除。
4. 必须预注册：损坏对象类型、剂量、随机种子、配对方式、主要结局（residual 恢复、verified 率、failed 率、兄弟保全）。

### BEMULA 的来源记录到底是什么形态

这是特别问题③的核心，必须把三件事分开：

1. **BEMULA 原始文件里有标注。** 对话 turn 带 `linked_fact_ids`，请求带 `target_fact_ids`，profile 事实带来源/派生元数据。
2. **ProvPurge 在合法评测中不能用这些标注。** 规格书第 10.2 节只允许系统读取 speaker、text、timestamp；标注在加载层丢弃。
3. **ProvPurge 的“来源记录”是它自己写时生成的。** 每条事实、向量块和摘要句的来源锚来自抽取器给出的轮次与句序，本质上是系统估计，不是基准提供的真实来源表。

因此，官方 BEMULA 中并不存在一个现成的实验条件叫“这条请求的来源记录被弄缺了”。系统当然会自然发生抽取漏检、置信低和闭包—检索不一致，`provenance-incomplete` 也会自然触发；但这种触发是**内生的**：

- 同一个抽取器既决定来源图，又决定完备性标记；
- 标记阳性的请求本来就更长、更绕、更难删；
- 没有独立金标证明某个阳性真是来源不完备、某个阴性真是完备；
- 直接比较阳性与阴性组的残余恢复，只能说明检测器挑出了一组高风险请求，不能证明拒提交规则导致了改善。

所以官方 BEMULA 对 A 最多支持三类描述性结果：标记分布、标记组的轮次/failed/残余情况、规则开/关在自然触发样本上的配对差异。最后一项仍受“哪些请求触发由系统内生决定”的限制，论文措辞必须克制。

### 能测 A 的自建注入实验应该怎么做

可行的处理变量不是“删掉输入文本”，而是**保留记忆内容、损坏内部来源结构**：

| 注入层级 | 做法 | 测什么 | 效度判断 |
|---|---|---|---|
| L1 来源边/锚损坏 | 正常 ingest 后，随机移除或错置一定比例的 `derived-from`、`summarizes` 边，或清空部分节点的来源锚 | 闭包在来源图不完备时是否漏删、完备性检查能否发现、拒提交是否迫使扩展覆盖 | **最推荐**：内容仍在，任务仍是删除已存信息 |
| L2 抽取节点缺失模拟 | 保留原始向量块/摘要句，但不生成对应事实节点或不登记其来源关系 | 模拟抽取漏检后的跨层残留 | 可做，但要保证目标仍可由残留层恢复，否则会把任务变简单 |
| L3 输入句子缺失 | ingest 前直接不给系统某些来源句 | 测“从未存入”而非“来源不完备” | **不适合作为 A 的主证据**，容易把遗忘变 trivial |

推荐设计：

- 在同一 ingest 快照上分支，先随机损坏 0%、10%、25%、50% 的来源边/锚，再分别运行“普通闭包可提交”和“完备性检查 + 拒提交扩候选”两臂。
- 随机化单位优先按请求所涉来源子图；若同一实例内请求共享节点会互相污染，则按实例分配剂量或每请求从快照独立分支。
- 结局同时看残余恢复下降和代价：verified 率、failed 率、额外轮次、额外删除数、兄弟保全下降。只看残余下降会把“全部拒绝提交”误报成成功。
- 注入清单只保存在实验控制器和结果 manifest 中，不进入 adapter 的运行时输入。

### 最可能翻车的点

1. **检测器自证。** 用同一套抽取/检索信号定义“不完备”，又用它证明规则有效；审稿人会认为这是循环论证。触发条件是只报官方 BEMULA 的自然分层、不做外部注入。
2. **规则只会拒绝，不会修复。** 来源边已经缺失时，继续沿同一张缺边图扩候选可能永远找不到残留；结果只是 verified 变 failed、RPR 下降，残余恢复没有实质下降。
3. **触发率失衡。** 阈值太松时几乎不触发，A 没有样本；太严时大部分请求都触发，系统普遍扩候选，成本与 failed 率爆炸。触发条件是长实例、F3 大作用域和低质量抽取底座。
4. **注入不像真实错误。** 随机删边与真实抽取漏检的分布不同：真实错误常集中在改写、跨 session、关系链和低显著度事实上。若只做均匀随机损坏，外部效度会被质疑。
5. **把“没存进去”误当“删干净”。** 若注入时连内容层一起丢掉，探针自然问不出，A 会被虚假证明。触发条件是 L3 式输入缺失或 L2 时把向量/摘要残留也一起移除。

### 降级方案

- A 降为**安全规则 + 失败模式分析**：保留 `provenance-incomplete`、拒提交和 failed 如实计数，不把它列为独立贡献。
- 实验只保留一个 L1 注入小实验：单一 25% 剂量、规则开/关配对、报告残余与 failed 的权衡。主张改成“来源结构损坏时，拒提交能以增加 failed 为代价降低错误 verified”，不声称已解决自然发生的来源不完备。
- 若注入实验也来不及，论文只写规格动机、自然触发分布和典型案例，并把因果验证列入局限与未来工作；此时 A 不能进入贡献清单。

**特别问题③结论：BEMULA 的原始对话与标注形态不能直接测 A——合法运行时来源图是 ProvPurge 自建的，官方数据没有可控的不完备条件；可信证据必须来自“保留内容、损坏来源边/锚”的自建注入实验。**

## 4. 贡献三（B）：F4 源—结论双语义删除

### 判定：有条件可做

### 实现难度与工作量估计

- 增量：**1.5–3 人周**。
- 主要工作不是删除本身，而是：触发解析增加语义字段、13 条 F4 请求的人工语义标注、防再推导墓碑、读路径拦截、两组再推导探针、双语义分项报告。
- 若另建一套 F4 类合成评测来扩样本，需再加 **1–2 人周**，且它只能称自建附加评测，不能冒充 BEMULA 官方结果。

### 算力与成本风险

- 直接算力增量小：F4 只有 13 条请求，按每条额外 2 道再推导探针，每轮约 26 次回答；即使多轮，也不是全项目成本瓶颈。
- 真正成本在错误归因：语义识别错一条就是 F4 样本的 7.7 个百分点；任何“显著改善”都很容易被一两条请求翻转。

### 依赖与前置条件

1. **语义金标必须独立于系统输出。** 在看结果前，由人工根据请求原文把 13 条 F4 标为 `conclusion-only`、`source` 或 `ambiguous`；最好有第二名标注者，至少报告一致性。Joseph 一人可完成初标，但一人自标自评的说服力有限，13 条量很小，请导师或同学复核的成本不高。
2. 结论在系统里要有可操作表示：显式结论节点、摘要句、或 query 时的推导路径。三者都没有时，B 只能做读时抑制，不能说完成了“结论删除”。
3. 防再推导墓碑不能把源事实本身变成不可答；源事实直接问答必须作为保全探针单独通过。
4. `ambiguous` 请求必须预先规定处理方式并单独报告，不能事后把不利样本改标为 ambiguous。

### 最可能翻车的点

1. **请求本意并不明确。** 用户只说“忘掉你推测出的那件事”，未必表达了保源还是删源。触发条件是 F4 请求文本没有明确范围词；强行二分会制造并不存在的金标。
2. **样本量太小。** F4 只有 13 条，且还要再拆成两种语义和 ambiguous，任一子组可能只剩个位数。触发条件是把子组通过率当确认性结论；统计上只能做描述性报告和案例分析。
3. **防再推导被审稿人判为“藏匿而非删除”。** 若结论没有存储节点、只靠读时墓碑拦截，审稿人会问与普通输出过滤有何区别。必须把“结论节点/摘要句已删”和“防再推导拦截”分开报告，不能混成一个删除成功。
4. **墓碑本身泄漏或误伤。** 墓碑若把源槽位集合与结论类型组织得过于具体，出口扫描和上下文处理可能间接暴露被删结论；拦截过宽又会阻止用户询问源事实或进行无关推理。
5. **语义解析错误主导结果。** F4 的主要失败可能不是删不净，而是 parser 把 `conclusion-only` 与 `source` 判反。必须把语义识别准确率、低置信率与删除效果分开，否则 B 的机制效应无法归因。

### 降级方案

- B 保留在方法中作为**语义设计与附加分析**，不列为强贡献：报告 13 条 F4 的语义分布、双语义通过率、语义识别错误和 2–3 个典型案例。
- 若人工标注一致性差或 ambiguous 占比高，取消双语义定量比较，只保留“系统支持两种操作语义”的设计说明与案例。
- 若需要更强证据，另建 60–100 条自生成 F4 类案例，请求文本明确写出保源/删源意图；结果单独成节，明确其为受控合成评测，不与 BEMULA 官方 F4 混算。

## 5. 贡献四 C1：留出探针泛化缺口

### 判定：有条件可做

### 实现难度与工作量估计

- 增量：**2–4 人周**。
- 构成：留出变换族设计与生成器、与门控集的难度匹配、阳性对照流程、加密/哈希密封、解封运行、配对统计与敏感性分析。
- 若要逐条人工审校 566 道留出探针，按每道 1–2 分钟，仅审校就约 9–19 小时；而且人工看过内容后，“对生成者密封”的强度会下降。更现实的做法是只在自生成开发目标上人工打磨模板与 rubric，BEMULA 留出集只做自动 schema 检查和阳性对照筛选。

### 算力与成本风险

- 新增约 **1,698 次回答 + 405–1,698 次 judge**，相对写入路径不是主要成本。
- 若阳性对照需要单独构建“已存入未删除”世界且没有快照复用，额外 ingest 才是大头。应在每条请求触发、该笔删除事务执行前，由隔离运行器对当时内存快照只读运行 gate 与 holdout 阳性对照；研究者只看聚合校准结论，不看留出题目和逐项结果。
- 留出探针不能进入扩候选回路；一旦用留出结果调阈值、改模板或决定是否扩候选，它就不再是留出集。

### 依赖与前置条件

1. **顺序必须写死**：先冻结门控探针生成器、判定合同、轮次上限和候选扩展规则；再冻结留出集生成器、种子派生与密封方式。正式运行中，留出题目只由隔离运行器在每笔事务删除前对快照执行阳性对照、并在该事务最终状态执行一次 post 检查；研究者不查看题目或逐项结果，留出结果不得反馈到候选扩展、阈值或模板修改中。
2. 留出集与门控集按同一 target fact/请求配对，尽量匹配跳数、答案形式、线索数量、问题长度和是否需要 residual 直喂。
3. 密封至少包含：生成代码版本、随机种子派生规则、题目文件哈希、生成时间戳、解封时间与运行 manifest。把哈希先提交到 Git 或请导师保存解密口令/校验值，能显著提高一人自封的可信度。
4. 预先规定阳性对照的等难标准与失败处理，例如两组删除前恢复率差的置信区间须落在预设等价界值内；不满足时报告调整后的差分或判定 C1 证据无效，不能事后挑一个有利口径。

### 一个人到底能不能做密封

**能做“流程可信”的密封，不能做“对手级”的自我盲法。**

同一个人设计了门控集，也知道留出变换族的大类；即使题目实例被加密，设计者仍可能在潜意识里让门控方法对这些变换族更友好。因此论文不能把 C1 写成第三方盲测。可信度来自程序约束，而不是声称自己“不知道”：

- 变换族和生成规则在正式运行前冻结并留时间戳；
- 题目实例自动生成后立即哈希并加密，运行前不打开；
- 自动检查只验证字段完整、答案键存在、无重复，不展示题目内容；
- 解封、运行和统计脚本一次执行，日志保留；
- 若导师愿意，解密口令或哈希校验值由导师保管，这是最低成本的外部见证。

如果 Joseph 在解封前因调试打开过留出题目、或用留出结果改过任何阈值，C1 必须降级为普通“额外探针集”，不能再称密封留出。

### Δ 的统计学能不能站住

先定义清楚：

\[
\Delta = Leak_{holdout,post} - Leak_{gate,post}
\]

它的有效样本量不是 566 道题。题目按请求聚合，请求又嵌套在 50 个实例中；同一实例的请求共享记忆、删除顺序和兄弟事实。规格书已经规定实例级 cluster bootstrap，这是正确口径，但也意味着有效信息量接近 50 个 cluster，而不是 566 个独立样本。

规划量级的判断：

- 若删除后 gate 泄漏率在 10%–30%，两组配对差的 95% CI 半宽很可能在 **8–16 个百分点**量级；实例聚类强、子组不一致时还会更宽。这只是规划判断，最终必须用试跑的配对 discordance 与 cluster bootstrap 实测，不能当成已得结论。
- 因此 C1 能较可信地发现 **10–15 个百分点以上**的泛化缺口；若真实缺口只有 3–5 个百分点，BEMULA full 的规模大概率只能得到“不确定”，不能证明没有过拟合。
- F4、F3 等分型 Δ 基本没有统计功效，只能描述，不应逐型下结论。

阳性对照也不是“两组 p 值不显著”就等于等难。正确做法是：

1. 删除前在同一内存快照上运行 gate 与 holdout，得到 \(Leak_{gate,pre}\) 与 \(Leak_{holdout,pre}\)。
2. 用等价性检验或 cluster bootstrap CI 判断删除前差异是否落在预设界值内，例如 ±10 个百分点；界值须在看正式结果前冻结。
3. 若删除前差异不可忽略，主报告同时给原始 \(\Delta_{post}\) 与差分调整值：
   \[
   \Delta_{adj}=\Delta_{post}-\Delta_{pre}
   \]
   但这属于对当前 C1 定义的统计修订，须先经 Joseph 同意并写入规格/实验计划，不能结果出来后临时换指标。
4. 删除前恢复不了的 target/probe 要按预注册规则处理。若 gate 与 holdout 的无效题比例差异很大，等难校准失败，不能靠简单删题把两组修到相等。

### 最可能翻车的点

1. **变换族不同源但难度也不同。** 留出题若更依赖多跳、别名或组合线索，\(\Delta>0\) 可能只是题更难，不是门控过拟合。触发条件是阳性对照差异大或匹配变量失衡。
2. **变换族其实与门控集同源。** 若只是换同义词、换问句模板，留出集与 BEMULA 五类攻击/门控四类高度重叠，\(\Delta\approx0\) 也证明不了泛化。触发条件是生成模板共享同一提示词骨架。
3. **密封被调试污染。** 任何一次“先看几道题确认质量”都可能让设计者针对性调整。触发条件是没有哈希时间戳、解封日志或外部见证。
4. **删除顺序与状态干扰。** 同一实例多个请求依次删除，后一个请求的留出探针面对的是累计删除状态；把每道题当独立样本会严重低估不确定性。
5. **阳性对照本身改写状态。** 若探针 query 被写入记忆或触发摘要更新，校准会污染正式状态。必须在快照/只读模式运行，并用写计数断言验证。

### 降级方案

- C1 保留为**泛化诊断**而非强结论：报告 \(Leak_{gate}\)、\(Leak_{holdout}\)、原始 \(\Delta\)、删除前差异和 cluster CI；CI 跨 0 或校准不稳时只写“未观察到可区分的大缺口”，不写“证明不过拟合”。
- 若等难校准失败，取消 \(\Delta\) 的因果解释，把留出集改称“未见探针压力测试”，只报告绝对泄漏率。
- 若密封流程无法由导师见证，仍可做自动生成 + 哈希时间戳版本，但论文中如实写明“程序性密封，非独立盲测”。

**特别问题②结论：C1 一个人做得出来，前提是模板化生成、自动质检、哈希/加密密封和导师见证；统计上它只站得住“大缺口”结论，几个百分点的 Δ 在 135 个请求、50 个实例的聚类结构下大概率不可分辨。**

## 6. 贡献四 C2：回执可验证性评测

### 判定：有条件可做

C2 的限定版是所有贡献里工程确定性最高的一条：签名、规范化、哈希、缺席扫描和故障注入都不依赖底座模型能力。风险主要来自威胁模型是否可信、验证器是否真的独立，以及是否把“能验篡改”夸大成“能证明删除”。

### 实现难度与工作量估计

- 限定版增量：**2–4 人周**。范围包括独立验证器、四档验证器对照、五类攻击中的关键攻击、预算—假接受关系。
- 全量版增量：**4–6 人周**。若再要求每张回执完整探针复检、所有攻击多剂量重复、跨存储版本新鲜性测试，工作量继续上升。
- 回执签发本身已计入主贡献；这里只计独立验证与攻击评测的增量。

### 算力与成本风险

- 签名、Merkle、canonical JSON、存储缺席扫描成本可忽略。
- 探针复检是唯一大头：全量 135 张回执约 **971 次回答 + 135–971 次 judge**；抽样 30 张约 216 次回答。
- 攻击注入若只操纵回执、日志和存储副本，几乎不耗模型；只有“删后写回”和状态新鲜性攻击需要重新运行读路径/探针。

### 依赖与前置条件

1. 回执必须绑定：事务 ID、存储版本/快照标识、删除集哈希、探针集预承诺哈希、逐层删除哈希、判定合同版本和最终状态。缺少存储版本绑定时，“旧回执重放”与“合法历史回执”无法区分。
2. 验证器应走独立的原始存储扫描路径，至少不能只调用删除器自己的 `exists()` 接口；否则删除器 bug 或假实现会同时骗过验证器。
3. 威胁模型先写清：C2 防的是实现错误、日志/回执篡改、范围遗漏、重放和删后写回；**不防掌握签名私钥的恶意签发者**。私钥持有者可以签一张内容全假的成绩单，单靠 Ed25519 无法阻止。
4. 假接受的分母、攻击剂量和验证预算须预注册；不能只展示“攻击全部被抓”的成功案例。

### 最可能翻车的点

1. **攻击像自导自演。** 若攻击只是把回执里一个字段删掉，而验证器本来就检查该字段，检出没有信息量。触发条件是攻击不经过真实存储、索引、日志和版本状态，只改 JSON。
2. **验证器与删除器共用同一套有 bug 的代码。** 例如向量删除只打标记，删除器和验证器都查标记而不查底层索引，两边会一致地误判已删。触发条件是缺席检查不做原始索引扫描或快照 diff。
3. **新鲜性误报。** 删除后用户合法写入同槽新值、做知识更新或再次删除时，旧回执的探针复检可能失败；这不一定是回执造假。没有存储版本和事务顺序，C2 会把正常演化误判为写回攻击。
4. **探针复检与原成绩单不可比。** judge 版本、判定合同、摘要重建状态或底座版本变化后，复检结果不同可能来自环境漂移，而非回执不实。复检 manifest 必须与原回执逐项比对。
5. **把防篡改说成证明删除。** Merkle + 签名只能证明“这张成绩单没被改过、由某私钥签发”，不能证明成绩单内容真实。C2 的价值在分层复核，不在密码学构件本身。

### 降级方案

- C2 压缩为一节：保留完整性/完备性/新鲜性三分解、四档验证器对照、两类最关键攻击——**日志完整但行未真删**、**删后又被写回**；其他攻击只做单元级故障注入，不做大规模模型复检。
- 验证对象抽样须在看结果前固定，例如按 F 类型与实例长度分层抽 30 张回执；论文明确写抽样评测，不声称全量独立复检。
- 若独立原始扫描来不及，至少让验证器直接读取存储快照文件/向量索引元数据，不调用删除事务模块的查询接口；并把“验证器与实现未完全独立”列为局限。

### C1+C2 合并版的额外判断

合并叙事是成立的：C1 防“成绩单被门控题刷出来”，C2 防“成绩单被伪造或蒙混”。但全量合并会同时引入两套独立证据链、两套统计/威胁模型和两倍评测对象。

- **全量合并：高风险。**
- **C1 完整 + C2 压缩：有条件可做，增量约 4–7 人周。**
- 合并时共用探针运行器、回执 manifest 和故障注入框架，能省约 1–2 人周；省不掉的是 C1 的校准统计与 C2 的独立验证器。

## 7. 定位性决策：LoRA 不进主方法

### 判定：有条件可做（仅可选消融）

### 实现难度与工作量估计

- 默认不启用：**0 人周**，这是当前最合理的选择。
- 一旦启用：**1.5–3.5 人周**，包括自生成训练/开发数据、标注规范、LoRA 训练与版本管理、识别指标、端到端对照和公平性说明。

### 算力与成本风险

- 32B 底座即使只训 LoRA，也要保存底座、优化器状态并反复前向/反向；5×3090 能做不等于值得做。训练本身可能不是最大成本，数据构造、错误分析和多版本对照才是。
- LoRA 识别器若只在某一个 Qwen 版本上训练，底座版本一旦在试跑后更换，适配器和全部识别结论都要重做。

### 依赖与前置条件

1. 先有提示版试跑的完整失败归因，且触发识别错误占比最高并明显高于删不净错误。
2. 训练数据与 BEMULA full、lite、quick_check 零重叠，且不能把 BEMULA 请求原文改写后冒充独立数据。
3. 对照必须同时报告识别 F1、F4 语义准确率、低置信未执行率和端到端 RPR/Score；只涨分类指标不算成功。

### 最可能翻车的点

1. **瓶颈根本不在触发识别。** 若主要失败是候选覆盖或探针后仍恢复，LoRA 再准也不改善主结果。
2. **自生成数据分布不匹配。** 合成请求的表达风格比 BEMULA 更规整，开发集涨分、正式集不涨。
3. **公平性质疑。** ProvPurge 独享额外监督信号，而基线没有对应训练组件；即使数据零重叠，审稿人也会问增益来自事务机制还是监督分类器。

### 降级方案

- 不启用 LoRA，不做任何解释性妥协；只在论文中保留“冻结底座、提示词识别”的定位。
- 若触发识别确为瓶颈但 LoRA 不划算，优先改提示词、确定性模式与低置信策略；这些属于主系统调优，不包装成额外贡献。

## 10. 总建议与实施顺序

### 10.1 总建议

**不要全做。先把主贡献做成一个成本受控、证据链完整的系统；第二贡献只保 C1，C2 压缩，B 做描述性附加，A 先降级。**

### 10.2 推荐顺序

1. **决策冻结（M1 前）**：骨干版本/量化、judge 归属、最大轮次初值 2、每请求探针与兄弟数、主表基线清单、辅助协议保留范围。未定版前不要进入大规模实现。
2. **主贡献最小闭环（M1–M3）**：先完成写入—来源—闭包—硬删—探针—回执—缺席检查。B 的语义字段和防再推导分支顺手纳入，但不为 B 单独扩建评测。
3. **受控试跑（M5 的第一小步）**：只测四件事——抽取/来源质量、单请求探针轮次与调用分布、judge 可靠性、失败归因。试跑结果决定轮次上限、底座部署和 LoRA 是否触发。
4. **C1 预留与密封（正式主跑前）**：门控配置、留出生成器、等难标准和失败处理必须在正式主跑前冻结并完成密封；阳性对照由隔离运行器在每笔事务删除前执行，研究者只看聚合结论。C1 的流程必须在正式运行前接入，事后补做会失去留出意义。
5. **正式主跑 + B 描述性分析**：同一批结果中提取 F4 双语义分项、语义错误与案例；不要为 B 再单独跑一套 full。
6. **C2 压缩版**：用正式运行产生的回执做四档验证器对照，集中打“行未真删”和“删后写回”。
7. **A 注入实验（有余力才做）**：先做 L1 单剂量配对，再决定是否扩到多剂量。若主贡献或 C1 尚未站稳，A 只保留规则与描述性结果。
8. **LoRA（默认不做）**：只有试跑归因满足写死条件才启动；否则把时间留给主结果复核、裁判人工抽查和论文写作。

### 10.3 开工前必须由 Joseph 拍板的五件事

1. 骨干：Qwen3-32B 级的具体版本、INT4 单卡多副本还是 BF16 跨卡。
2. judge：内部探针与官方评测分别用本地还是 API；若本地，是否接受与 agent 不同家族的第二模型部署成本。
3. 成本上限：最大轮次先定 2 还是 3；每请求最大探针数、最大新增删除数和整轮 token/调用预算。
4. 主表基线：先做 4 个核心基线，还是坚持更多基线并接受周期拉长。
5. 第二贡献范围：推荐“C1 完整 + C2 压缩”；若只能二选一，是否确认保 C1。

## 11. 评估依据与不确定性说明

### 11.1 本报告使用的硬事实

- 方法与贡献范围以《ProvPurge 方法规格书》和《ProvPurge 创新点定稿与代码实现方案》为准；规格书明确第二贡献在规格层仍待选择，创新方案中的 C1+C2 合并版是当前推荐版，不是已冻结规格。
- BEMULA 规模、协议与仓库事实来自既有核查报告和本地仓库静态计数：50 实例、两版各 746 sessions/36,900 turns、135 请求、1,742 题、官方 query 2,922 次、LLM judge 2,895 次、judge 温度 0、`probe_writeback=false`、Lite 为 full 子集、quick_check 为独立 tiny 实例、`memoryos.py` 缺失、默认 agent 模型口径与本地 embed 选项。
- BEMULA 无官方成本/时长数据。本报告所有美元以外的“成本”均指调用量、token 下限、机器占用与人力，不把调用数冒充实测时延。
- MemCut 只作 residual 辅证且官方代码未公开；其 39–76% 残余恢复与覆盖瓶颈用于说明探针/residual 的必要性，不被当作 ProvPurge 已获得的结果。

### 11.2 本报告的估计不是事实

- 人周、探针 judge 的批量/逐项区间、Δ CI 的 8–16 个百分点规划量级，都是为决策做的估计，必须在获准试跑后用真实分布替换。
- “session 批处理能降调用数”不等于已证明能保持相同抽取质量；长 session 的结构化输出失败率必须实测。
- “快照分支能省写入成本”以存储实现支持完整、隔离的快照为前提；若 M1/M2 未预留该能力，后期补做会产生返工。

### 11.3 最终判断

ProvPurge 的主线没有原则性不可行：它不训练模型、核心算法大多是确定性工程、最难的探针门调用量本身可数且可封顶。真正的可行性边界在四处：**长会话抽取与来源对齐、待验事务的隔离/回滚语义、Qwen 底座与 judge 的可靠性、全项目重复运行的乘数成本**。把范围按本报告收缩后，主贡献与 C1 是一名硕士生可以认真做完的组合；把所有定稿内容全量展开，则更像多人项目或多阶段路线图，不应作为一轮论文工作的默认承诺。

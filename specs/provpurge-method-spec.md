# ProvPurge 方法规格书

> 本规格为第 3 关文档，未经 Joseph 点头不进入实验。本文件只写规格，不含代码，不报告任何实验结果。后续实现与论文方法章均以本文件为共同依据；与本文件冲突的实现视为偏离规格，须先修订本文件再改实现。

## 0. 定版前提

本节冻结的内容不在实现阶段重新讨论。变更须由 Joseph 批准，并同步修订本文件版本号与变更记录。

**基准定版。**

- 主基准为 BEMULA，主指标为其官方指标 RPR 与 Score。所有主表结论只基于 BEMULA。
- 辅助协议一为 LongMemEval-S 的知识更新子集，共 78 条，用于检验知识更新场景，不进主表排序。
- 辅助协议二为 STALE 子集，用于检验陈旧信息处理，不进主表排序。
- LoCoMo 只做 sanity check，用于确认系统在通用长对话记忆任务上没有明显退化，不作任何优劣宣称。
- MemCut 只做辅证：借用其 residual 直喂协议验证删除后的残余恢复情况，结果单独成节报告，不进主表，不与 BEMULA 指标混合计算。

**创新内核定版。** ProvPurge 的唯一核心主张是 probe-gated 硬删事务：删除不以“已执行删除动作”为完成标准，而以“预先承诺的攻击探针集全部无法恢复目标信息、且无关记忆保全探针全部通过”为提交条件。来源图、实体扩展与回执都是为这一提交条件服务的组件，不单独宣称首创。

**不完备来源下的口径收窄（2026-10-30 并入 A）。** 本规格的创新表述为“在来源不完备条件下仍以探针结果为准绳的闭包删除”。全文不得再出现以“来源完整”为前提的表述，不得宣称因来源记录完整所以删除必然完备。闭包是候选生成的一种手段，其完备性不被假设；最终是否删净只由探针门判定。该收窄源于 AfterDeleteBench（arXiv:2610.31366）的结果——其闭包重构结论以来源记录完整为前提，不覆盖来源不完备情形；ProvPurge 针对的正是来源锚缺失、抽取有漏等不完备情形。

**硬件与骨干定版。**

- 计算资源为本地 5 张 RTX 3090，每张显存 24 GB。本论文不训练模型，全部计算为推理与评测。
- 模型服务由 vLLM 提供 OpenAI 兼容端点，系统与基线均通过该端点调用，不直接绑定某一推理框架的私有接口。
- 骨干模型为 Qwen3-32B 级。具体版本在试跑阶段定版，定版后写入第 12 节的决议栏。部署方式二选一：量化版单卡部署，或原精度跨卡部署。评测时优先开多个模型副本并行处理互相独立的实例，而非把全部卡捆成单个模型。
- 嵌入模型为本地 BGE-M3 级，本地部署，不调用外部嵌入 API。
- 公平性约束：所有进入主表的基线必须在同一骨干模型、同一嵌入模型、同一服务条件下重跑。引用基线原论文中基于其他骨干得到的数字时，只能放在相关工作讨论中，不得与主表数字直接对比。

**验收标准。**

- 实现仓库的配置说明中能逐项对应本节的基准、骨干与嵌入设置。
- 任何主表数字都能追溯到同骨干重跑的日志，而非引用外部数字。

## 1. 系统总览与数据流

ProvPurge 是一个带可验证删除能力的长期记忆系统，由四条路径组成。

**写入路径。** 对话轮次进入系统后，依次经过事实抽取、分句、来源登记与三层落盘。落盘的三层是事实层、向量层与摘要层。三层中的任一对象都必须携带来源锚。写入路径的详细规格见第 3 节。

**触发识别路径。** 每一轮用户输入在进入普通问答处理之前，先经过触发识别。识别器判断该输入是否为遗忘请求或知识更新请求，并解析其作用域。若不是删除或更新请求，输入按普通轮次进入写入路径或读路径。若是，则生成一个删除或更新请求对象，交给删除事务处理。详细规格见第 4 节。

**删除事务路径。** 给定一个请求对象，系统先由请求与当前记忆状态构造探针集并做哈希预承诺，再生成候选删除集，在三层上执行硬删，然后运行探针门。探针门通过则事务提交并签发回执；不通过则自动扩大候选集并重复删除与验证，直到通过或达到最大轮次上限。详细规格见第 5、6、7 节。

**读路径。** 用户提问进入系统后，先做检索，再依次经过墓碑过滤、上下文组装、骨干模型生成、答案出口扫描与陈旧前提检查，最后返回答案。读路径不得修改任何已入库记忆。详细规格见第 8 节。

文字流程如下：

```text
对话轮次
  -> 触发识别
       |- 普通轮次 -> 写入路径 -> 事实层 / 向量层 / 摘要层
       |- 遗忘或更新请求 -> 删除事务
       |     -> 探针集构造与哈希预承诺
       |     -> 候选生成（来源图闭包 + 实体扩展）
       |     -> 三层硬删（待验状态）
       |     -> 探针门验证
       |           |- 全过 -> 提交 -> 签发探针成绩单回执
       |           |- 不过且未达轮次上限 -> 扩大候选 -> 再次硬删与验证
       |           |- 不过且已达上限 -> 标记未通过（不提交） -> 签发 failed 回执
用户提问
  -> 检索 -> 墓碑过滤 -> 生成 -> 出口扫描与陈旧前提检查 -> 答案
```

四条路径之间只有两个共享状态：来源图与墓碑表。写入路径只向两者追加，删除事务是唯一可以删除来源图节点与写入墓碑的组件，读路径只读两者。这一约束保证任何记忆的消失都必然对应一个可审计的删除事务。

**验收标准。**

- 任一记忆对象的删除都能对应到唯一的删除事务记录。
- 读路径的代码路径中不存在对事实层、向量层、摘要层或来源图的写操作。

## 2. 数据结构

### 2.1 句级来源图

来源图是有向图，节点分三类。

| 节点类型 | 内容 | 所在层 |
|---|---|---|
| 事实条目 | 一条原子事实，含槽位与取值 | 事实层 |
| 向量块 | 一段文本及其嵌入向量 | 向量层 |
| 摘要句 | 摘要中的一个句子 | 摘要层 |

每个节点必须携带以下字段，缺一不得入库：节点标识、节点类型、所属槽位（无槽位的节点填空值并注明原因）、来源锚、创建时间、当前版本号。

来源锚由两部分组成：对话轮次标识与句序。句序指该节点内容在来源轮次文本中所属句子的序号，从 0 开始计数。同一轮次产生多个节点时，各节点的句序必须能区分其来源句子；一句产生多个事实条目时，这些条目共享同一句序。

**无来源不入库原则。** 任何无法确定来源锚的内容不得写入三层中的任何一层，也不得进入来源图。该原则没有例外通道；实现中不得提供跳过来源登记的开关。

### 2.2 边类型

来源图只允许三类边，新增边类型须先修订本规格。

- `derived-from`：由派生物指向来源。例如一条事实条目由某向量块抽取得到，则从事实条目到向量块连一条 `derived-from` 边。全部该类边方向统一为派生物指向来源。
- `summarizes`：由摘要句指向被其概括的事实条目或向量块。一个摘要句可连多条该类边。
- `same-slot` 版本边：同一槽位的不同版本之间按版本号顺序相连，旧版本指向新版本。该类边构成第 2.4 节的版本链。

每条边必须记录创建它的操作类型：写入、摘要生成或知识更新。

### 2.3 槽位与墓碑表

槽位（slot）是知识更新与遗忘的作用单位，形式为“实体—属性”对，例如某人的居住城市。槽位的命名由写入路径的抽取结果决定，同一实体同一属性在全系统内必须使用同一槽位标识。

墓碑表记录已被删除或被取代的旧值，每行字段如下：

| 字段 | 含义 |
|---|---|
| slot | 槽位标识 |
| old_value | 被删除或被取代的旧值原文 |
| request_id | 触发本次删除或更新的请求标识 |
| timestamp | 墓碑写入时间戳 |
| reason | 取值为 forget 或 superseded |

墓碑只增不删。删除事务回滚时不删除已写墓碑，而是追加一条回滚记录。墓碑表是读路径防御的数据依据，见第 8 节。

**防再推导墓碑（F4 双语义，2026-10-30 并入 B）。** 当遗忘语义为 conclusion-only 时（见第 4 节），除普通墓碑外，还须为（源事实集合，结论类型）登记一条防再推导墓碑，字段至少包含：源槽位集合、结论类型、被删结论的标识哈希、request_id 与 timestamp。其作用不是删除源事实，而是供读路径在回答将重新推出该结论时拦截（见第 8 节）。删源事实（source 语义）时不登记此类墓碑，源与结论按普通删除事务处理。

### 2.4 版本链与知识更新

同一槽位的多个取值按写入时间构成版本链，由 `same-slot` 边连接。链上只有最新版本处于 active 状态，其余版本处于 superseded 状态。知识更新发生时，系统写入新版本事实条目，将旧版本置为 superseded，向墓碑表追加一行 reason 为 superseded 的记录，并按删除事务的同一套探针门验证旧值已不可被恢复。也就是说，知识更新在实现上复用删除事务，区别仅在于多写入一个新版本，且墓碑的 reason 不同。

**验收标准。**

- 随机抽查任一节点，都能由其来源锚定位到原始对话轮次与句子。
- 不存在来源锚为空的节点；构造一个来源缺失的输入时，系统拒绝落盘并记录原因。
- 任一槽位的版本链可完整遍历，active 版本唯一。

## 3. 写入路径规格

写入路径按以下五步顺序执行，不得跳步。

第一步，接收轮次。输入为一轮对话，至少包含说话人、文本与时间戳。字段缺失时整轮拒绝处理并记录，不做猜测补全。

第二步，事实抽取。由骨干模型从文本中抽取原子事实，每条事实须给出槽位、取值与所依据的句子序号。抽取调用失败、返回不可解析或返回空结果时，本轮不落盘，并记录失败类型。抽取失败不得降级为“把整轮原文直接写入向量层”，因为那样会绕过来源登记。

第三步，分句。对轮次文本分句，得到句子序列与句序编号。分句结果是来源锚的依据，必须与抽取步骤引用的句子序号使用同一套编号。实现中抽取与分句须共享同一次分句结果，不得各自独立分句。

第四步，来源登记。为每条事实条目、每个向量块与每句摘要句生成节点，填写来源锚，并在来源图中连上相应的 `derived-from` 与 `summarizes` 边。任一节点无法确定来源锚时，整轮不落盘，并记录缺失来源的对象类型。

第五步，三层落盘。事实条目写入事实层，向量块写入向量层，摘要句写入摘要层。三层写入须作为一个整体：任一层写入失败时，已写入的层须撤销本轮写入，不允许出现只有部分层有本轮数据的不一致状态。摘要在本轮暂不生成时，向量层与事实层先落盘，摘要句节点在摘要生成时补登记，但其来源锚仍指向原始轮次与句序。

失败处理汇总如下：

| 失败情形 | 处理 |
|---|---|
| 抽取调用失败或不可解析 | 整轮不落盘，记录失败 |
| 抽取结果为空 | 整轮不落盘，记录为空结果 |
| 来源锚缺失 | 整轮不落盘，记录缺失对象 |
| 任一层落盘失败 | 撤销本轮已落盘内容，记录失败层 |

**验收标准。**

- 注入抽取失败与来源缺失两类故障时，三层均无该轮残留数据。
- 任一已落盘轮次的三层对象在来源图中均可达且来源锚一致。

## 4. 触发识别规格

BEMULA 的协议要求被测系统自己从自然语言中识别遗忘与更新请求，评测方不发送结构化的删除调用。因此触发识别是系统的一部分，其错误计入系统错误，不得在评测接入层用标注字段替代。

**识别任务。** 对每一轮用户输入，识别器输出一个结构化结果，字段如下：是否为删除或更新请求、请求类型、作用域、置信度、语义类型。语义类型字段取值为 `conclusion-only` 或 `source`（见下文 F4 双语义），对非 F4 类请求可为空但须显式标注不适用。识别器由骨干模型加固定提示词实现，提示词版本须随代码一同保存，变更提示词视为方法变更。

**类型映射。** 请求类型必须映射到 BEMULA 的六类遗忘类型 F1 至 F6，映射表以 BEMULA 官方对六类的定义为准，实现时逐类抄录官方定义到代码注释与实验附录中，本规格不另行改写其定义。此外单列一类知识更新（update）：用户给出同一槽位的新值以取代旧值。无法映射到 F1 至 F6 或 update 的输入不按删除处理。

**作用域解析。** 作用域输出包含三部分：目标槽位集合、目标实体集合、时间范围。时间范围可为空，表示不限时间。解析结果必须能直接被第 5 节的候选生成消费，不允许输出只有自然语言描述的作用域。

**F4 源-结论双语义（2026-10-30 并入 B）。** 遗忘请求按目标区分为两种语义，作用域解析必须输出语义类型字段（`conclusion-only` / `source`），候选生成、删除事务与探针门均按该字段分支处理：

- (i) `conclusion-only`：只删推导结论、保留源事实。删除结论节点，并为（源，结论类型）登记防再推导墓碑（见第 2.3 节）；源事实本身不进入删除集。
- (ii) `source`：删源事实。源进入正常删除事务，且其全部派生结论必须随之塌陷，即派生结论节点一并进入闭包候选（见第 5 节）。

无法判定语义类型时，不得默认按 `conclusion-only` 静默执行；按第 4 节低置信处理记录并保守处理。

**低置信处理。** 置信度低于阈值时按以下顺序处理，不允许静默执行删除：

1. 若输入同时包含明确的新值，则按知识更新的保守路径处理，只对能确定槽位的部分执行，其余部分不删。
2. 否则不执行删除，把该轮按普通轮次进入写入路径，并在日志中记录一次低置信未执行事件，包括原始输入、识别结果与置信度。
3. 低置信未执行事件的数量须在实验中单独报告，作为触发识别的误差来源之一。

置信度阈值的具体数值在开发集上确定，确定后冻结并写入实验配置。开发集的来源见第 10 节。

**验收标准。**

- 识别器对任意输入都输出包含类型、作用域与置信度的结构化结果，无自然语言形式的自由输出进入删除事务。
- 低置信输入不产生任何删除动作，且在日志中可检索到对应的未执行事件。

## 5. 候选生成规格

候选生成的目标是找出删除集，使得目标信息的所有可推导来源都被覆盖。用集合覆盖的语言说，目标是覆盖全部可推导集合的一个 hitting set：每一个能推出目标信息的证据集合都至少被删除集命中一个元素。候选生成不以固定 top-k 为目标，k 是结果，不是参数。

**双通道生成。**

通道一为来源图闭包。从作用域命中的槽位与实体出发，沿 `derived-from`、`summarizes` 与 `same-slot` 边做闭包遍历，得到与目标事实有来源关系的全部节点，包括其派生的摘要句与向量块。

**组件节点计入闭包（2026-10-30 并入 A）。** 闭包成员除事实节点外，还包括能组合出目标秘密的组件节点（components that could compose a secret count as closure members）：即单个节点本身不含目标值、但若干节点组合后可拼凑或推出目标秘密时，这些组件节点同样是闭包成员，须进入候选池并按覆盖目标参与删除集选择。当语义类型为 `source` 时，源事实的全部派生结论节点也必须作为闭包成员进入候选，确保源删除后结论随之塌陷。

通道二为实体扩展。从作用域中的实体集合出发，在实体关系上做 1 至 2 跳扩展，把与目标实体相邻、可能携带可推导证据的节点纳入候选。扩展跳数是参数，默认 1 跳，第 7 节的自动扩候选可将其提升到 2 跳。

**候选生成三条硬规则（2026-10-30 补读 MemCut 附录后定版）。**

- 实体扩展不受相似度 top-k 截断：实体通道命中的节点不得因其与目标的相似度排名靠后而被 top-k 截去。依据 MemCut 附录 D：其证据的相似度排名散至 3–141，pool20 只含部分 link 证据、pool50 才完成 cut，个别证据不入任何 ≤60 的池，而实体 1-hop 在其数据上全覆盖（其效果作者未测）。
- 关系链按每个中间实体逐个展开：凡关系链上的中间实体，须逐个作为扩展起点展开，不得只展开链首或链尾、也不得把整条链当作一个节点处理。
- 回执／日志按实体记录 1-hop 覆盖数：每个目标实体的 1-hop 邻居总数与已进入候选池的 1-hop 数须逐实体写入事务记录与回执（见第 9 节）。

上述取向亦与 MemCut 附录 B.4 一致：扩覆盖（pool 20→60，−12.50 点）远胜加预算（budget 10→20，仅 −1.39 点且多删 9.95），故候选阶段优先保证覆盖，而非优先扩大实际删除预算。

**池宽参数。** 候选池宽度可参数化，默认值为 60。该默认值依据 MemCut 的池宽扫描结论：候选池由 20 扩大到 60 时收益明显，而盲目增大删除预算有害。因此本规格把“扩大候选池”与“扩大实际删除集”分开：池宽决定可考虑的范围，实际删除集由覆盖目标决定。池宽的消融取值见第 11 节。

**删除集选择。** 在候选池内选择删除集时，优先级依次为：先选来源图闭包内的节点，再选能覆盖更多可推导集合的节点，最后选实体扩展通道的节点。选择过程必须记录每个被选节点的入选通道与理由类别。

**覆盖数报告。** 每个请求必须报告实际覆盖数 k，即该请求最终删除集命中的可推导证据数量，并同时报告候选池大小与实际删除数。三者写入事务记录，供论文按第 11 节要求分项分析。只报告删除数而不报告 k 视为不合规格。

**MemCut 残余公式的引用口径（2026-10-30 定版）。** MemCut 的 Res≈13(8.2−k) 在本文中只作 pooled 先验引用：该式为其 132 个设置的 pooled 拟合，其附录 B.3 无分类型独立参数。因此禁止给不同秘密类型分配不同权重系数。类型差异的表述改为 k 可达性差异：S2 后 Res 为 relation chain 71.8% 对 aggregation 24.3%，删中证据所需 turns 为 2.4 对 4.6；差异归因于不同类型的 k 可达性不同，不归因于类型专属系数。

**来源完备性检查（2026-10-30 并入 A）。** 候选生成完成后、执行删除前，须对每个请求做来源完备性检查。出现以下任一情形时，该请求标记为 `provenance-incomplete`，并把触发情形写入事务记录：来源锚缺失；抽取置信不足（低于冻结阈值）；闭包结果与检索结果不一致（检索召回了闭包未覆盖的、与目标相关的存活节点，或闭包节点在检索中完全无对应）。该标记不阻断删除执行，但直接约束探针门的提交条件，见第 7.3、7.4 节。不得以闭包已生成即默认来源完备。

**验收标准。**

- 任一事务记录中都包含候选池大小、实际删除数与覆盖数 k。
- 关闭实体扩展通道后，候选集严格等于来源图闭包，验证双通道可独立开关。
- 构造来源锚缺失、抽取置信不足、闭包与检索不一致三类用例时，均被标记为 `provenance-incomplete` 并写入事务记录。

## 6. 删除事务规格

**三层硬删。** 删除是硬删，不是标记隐藏。

- 事实层：删除事实条目的整行记录。
- 向量层：从向量索引中删除对应向量块，删除后该块不得再被任何检索召回。只在元数据上打删除标记而向量仍可召回，不算硬删。
- 摘要层：对包含目标内容的摘要句做外科式改写，只改动目标句；无法只改目标句时允许整段重生成，但重生成结果与原摘要的差异必须逐句比对，非目标句出现内容变化时该次改写判为失败并回滚。

**重建确定性（2026-10-30 补读 MemForm 后定版）。** 删除后的摘要重建／合并顺序必须确定性化：给定相同的保留集与删除集，重建的输入顺序、合并顺序与生成参数须固定且可复现，不得依赖调用时序、并发完成顺序或未记录的随机性。该重建／合并顺序须记入回执（见第 9 节）。兄弟保全探针必须在重建后状态上运行，不得在重建前的中间状态上运行后沿用其结果。依据 MemForm 的 Path 结果：保留集不变、仅合并顺序改变即可改变行为（ASR 37.1–95.1%），故顺序本身是须受控并留痕的变量。MemForm 是记忆形成端投毒工作，进必引作形成端威胁定位，不进基线。

**原子性与回滚。** 一个删除事务对三层的修改要么全部生效，要么全部不生效。执行顺序为先备份待删对象的标识与哈希，再逐层删除，最后统一确认。任一层删除失败，或摘要改写比对失败时，事务回滚到删除前状态，回滚本身也要写记录。不允许出现事实层已删而向量层未删的中间状态被读路径观察到：事务处于待验状态期间，读路径对涉及的槽位按已删除处理，对其他槽位不受影响。

**状态机。** 事务状态只有以下五种，转移必须按箭头方向发生并记录时间戳：

```text
candidate（候选已生成）
  -> deleted_pending（已删待验）
       -> committed（已提交，探针门通过）
       -> rolled_back（已回滚，删除失败或改写比对失败）
       -> failed（未通过，达到轮次上限，见第 7 节）
```

状态为 candidate 与 deleted_pending 的事务不得签发 verified 回执。状态为 failed 的事务，其目标信息视为未删除成功，必须在结果中如实报告。

**验收标准。**

- 人为注入任一层删除失败时，三层状态与事务前一致，且存在回滚记录。
- 摘要重生成后非目标句发生变化的用例被判失败并回滚。
- 事务状态转移日志完整，不存在跳过 deleted_pending 直接到 committed 的记录。

## 7. 探针门规格

探针门是本方法的核心组件。本节的每一条都是硬性规格，不允许在实现中以“近似等价”为由省略。

### 7.1 探针集预承诺

探针集必须在删除执行之前构造完成，并做哈希锁定。构造时点是：作用域解析完成之后、候选生成之前。锁定方式为对探针集的规范化文本计算哈希，记为探针集预承诺哈希，写入事务记录。删除执行之后不得增删或改写探针题目；确需修改时，必须回滚事务并以新事务重新预承诺。这一约束是为了防止事后挑题，即删不干净时悄悄换掉问得出目标信息的探针。

探针的构造只能使用删除前可见的信息：目标槽位、目标实体、目标旧值与无关记忆的抽样。不得使用任何评测标注字段，见第 10 节的白名单声明。

### 7.2 探针四类

每个请求的目标探针由以下四类组成，每类至少一题，题目总数与各类分布写入事务记录。

- 原生问答探针：通过系统自身的读路径提问，走正常检索与生成，检验目标信息是否还能被问出。
- Residual 直喂探针：绕过检索，把删除后仍然存活的、与目标相关的记忆对象直接作为上下文喂给骨干模型再提问，检验残余证据是否足以恢复目标信息。该类探针对齐 MemCut 的 residual 协议。
- 推导与多跳探针：不直接问目标值，而是问需要经过一至两步推导才能得到目标信息的问题，包括经由相邻实体或同一关系链推导的问法。
- 陈旧前提与攻击型探针：把目标旧值作为既定前提嵌入问题，或使用角色扮演、越狱式前缀等诱导问法，检验系统是否会顺着陈旧前提复述旧值。该类探针对齐 BEMULA 的攻击集问法类别。

另有一组兄弟保全探针，与目标探针分开计数：从与目标无关的槽位中抽样提问，检验无关记忆在删除后是否仍然完整可答。兄弟保全探针的抽样种子须记录，保证可复现。

**F4 双语义再推导探针（2026-10-30 并入 B）。** 对 F4 类请求，须在上述四类之外补两组多跳再推导探针，与语义类型一一对应：

- 对 `conclusion-only`：验证结论不可再被推出，且源事实仍可正常回答。探针须包含经由保留的源事实做一至两跳推导的问题——若回答重新推出被删结论，判为恢复成功；同时直接询问源事实的问题必须仍能答对，源被误伤判为保全失败。
- 对 `source`：验证源与结论均不可恢复。探针须同时覆盖源事实的直接与直喂问法、以及经由源推导结论的多跳问法，任一能恢复源或结论即判为恢复成功。

### 7.3 提交条件

事务提交当且仅当以下两个条件同时成立：

- 全部目标探针都无法恢复目标信息，即每道目标探针的回答都不包含目标值，也不包含能唯一推出目标值的等价表述。
- 全部兄弟保全探针都仍然答对，即无关记忆没有被误删或误伤。

探针判定由裁判模型完成，判定提示词与判定规则须冻结并随代码保存。判定为“包含等价表述”这类边界情形时，宁可判为恢复成功，即对删除方从严。

**探针判定双通道（2026-10-30 补读 AfterDeleteBench 附录后定版）。** 每道探针的成绩须双通道并记，不得只记单一判定：（一）解析判定——按冻结的答案格式／解析合同从回复中解析出答案后判定；（二）目标串全文出现检查（exact-target-anywhere）——在原始回复全文中检查目标串是否出现。判定合同（答案格式、解析规则与版本）须版本化，判定合同版本写入回执（见第 9 节）。两通道结果冲突时，以原始回复（raw）为准并标记复核，不得以解析判定覆盖原始回复中的实际出现。依据 AfterDeleteBench 附录：答案格式／解析合同错位曾使两个模型官方 0 分、但原始回复含目标分别为 77/104 与 78/104，只换合同可使提取数由 77/104 变为 0/104，甚至使 write 效应反号；只报解析判定会系统性漏报泄漏。

**组件级部分泄漏单独记账（2026-10-30 定版）。** 探针结果除全串恢复外，须单独统计组件级部分泄漏：目标秘密的任一组件被恢复即记为一次部分泄漏，与全串恢复分开计数，不得并入全串恢复数、也不得因全串未恢复而记为无泄漏。依据 AfterDeleteBench C3：缺组件时完整恢复为 0，但部分泄漏为 104/104。该计数写入回执字段 `partial_leak_count`（见第 9 节）。

**不完备来源的提交限制（2026-10-30 并入 A）。** 请求被标记为 `provenance-incomplete` 时（见第 5 节），探针门拒绝提交：即使本轮目标探针与兄弟保全探针表面全过，也不得直接签 `verified`；须先按第 7.4 节继续沿实体图扩候选并重删、重跑探针，直到目标探针全部无法恢复且来源完备性检查不再触发，或达到最大轮次上限。达到上限仍未满足时，事务置 `failed` 并如实记录，不得签 `verified`。

### 7.4 不过时的自动扩候选与轮次上限

任一目标探针恢复成功时，系统自动扩大候选：沿来源图与实体图再扩一跳，把新命中的节点加入删除集，重新执行三层硬删并重跑全部探针。兄弟保全探针不过时，不扩大候选，而是先检查删除集是否包含与目标无关的节点，剔除误入节点并回滚其删除，再重跑探针。

最大轮次上限为可配置参数，定版值在试跑阶段确定并写入实验配置，确定后冻结。每轮的候选增量、删除增量与逐项探针结果都必须记录。

对 `provenance-incomplete` 的请求，自动扩候选同样适用且为强制路径：系统继续沿实体图扩候选并重删，每轮重做来源完备性检查与全部探针；只有当探针全部无法恢复、兄弟保全全过、且完备性检查不再触发时才可提交。达到最大轮次上限仍不满足的，置 `failed` 并如实记录触发情形与每轮结果。

达到轮次上限仍有目标探针恢复成功时，事务置为 failed：保留全部轮次记录，签发 failed 回执（见第 9 节），并在结果统计中把该请求计为删除未通过。不允许把 failed 事务改记为成功，不允许丢弃其探针记录，也不允许在报告时把这类请求从分母中剔除。

**验收标准。**

- 删除后修改探针集的操作被拒绝，或必然触发事务回滚与重新预承诺，日志可查。
- 构造一个已知删不干净的用例时，系统发生自动扩候选并留下多轮记录。
- 达到轮次上限的用例最终状态为 failed，且在统计中计入分母。
- `provenance-incomplete` 的请求在完备性检查仍触发时不存在 verified 回执；其扩候选与重删轮次记录完整。
- F4 两组再推导探针均被执行并逐项记录，conclusion-only 用例中源事实问题仍可答对。

## 8. 读路径防御规格

读路径防御是删除之后的第二道防线，共三项。三项都只读墓碑表，不修改记忆。

**墓碑过滤。** 触发条件：检索结果中出现槽位与旧值同时命中墓碑表记录的对象。处理：该对象不进入上下文组装。误杀控制：只有槽位与旧值双双命中才过滤；仅槽位相同而取值是当前 active 版本的对象不得过滤。过滤次数按请求记录。

**答案出口扫描。** 触发条件：骨干模型生成的答案文本中出现任一与当前提问槽位相关的墓碑旧值。处理：该答案不直接返回，改为重新生成一次并在提示中显式排除该旧值；第二次生成仍出现旧值时，返回不包含旧值的拒答式回答，并记录一次出口拦截事件。误杀控制：扫描范围限于与提问相关的槽位对应的墓碑，不做全墓碑表的无差别字符串匹配，避免同名取值在无关语境下被误杀。

**陈旧前提拒绝。** 触发条件：用户提问把某个墓碑旧值当作既定前提，且该槽位当前 active 版本的取值与该前提不一致。处理：回答中先指出该前提已过期，给出当前版本或说明该信息已被删除，再回答其余部分；不得顺着陈旧前提继续推理。误杀控制：前提与当前版本一致时不触发；提问只是询问旧值是否存在时，按墓碑事实如实回答“已删除或已更新”，不触发拒绝话术。

三项防御的触发与拦截次数都须按请求记录，供第 11 节的消融与分项报告使用。

**防再推导拦截（F4 conclusion-only，2026-10-30 并入 B）。** 在上述三项之外，读路径还须查防再推导墓碑（见第 2.3 节）：当本次回答所依据的源事实集合与结论类型命中一条防再推导墓碑、且生成答案将重新推出该被删结论时，拦截该答案，按出口扫描的同等流程重新生成并显式排除该结论；仍推出时返回不包含该结论的回答并记录一次防再推导拦截事件。该拦截只针对被删结论本身，不得连带拒答源事实——直接询问源事实的问题仍须正常回答。拦截次数单独记录，不与三项防御混计。

**验收标准。**

- 已删除槽位的问题在检索阶段被墓碑过滤，不进入上下文。
- 诱导模型复述旧值的用例在出口被拦截并留下事件记录。
- 当前版本取值正常的问题不被任何一项防御误杀，抽查可验证。

## 9. 探针成绩单回执规格

每个删除事务结束时签发一张回执。回执签的是验证结果，不是删除动作本身。

**字段清单。** 回执必须包含以下字段，缺一不得签发：

- request_id 与事务标识；
- 闭包清单哈希：删除集所含节点标识清单的哈希；
- 探针集预承诺哈希，见第 7.1 节；
- 每轮探针的逐项结果：探针标识、探针类别、本轮判定结果；
- 兄弟保全结果：逐项结果与通过总数；
- 逐层删除哈希：事实层、向量层、摘要层各自被删对象标识清单的哈希，共三个；
- 候选池大小、实际删除数与覆盖数 k；
- 逐实体的 1-hop 覆盖数：每个目标实体的 1-hop 邻居总数与已进入候选池的 1-hop 数（见第 5 节）；
- `partial_leak_count`：组件级部分泄漏计数，与全串恢复数分开记账（见第 7.3 节）；
- 判定合同版本：探针双通道判定所用答案格式／解析合同的版本（见第 7.3 节），以及两通道冲突时的复核标记；
- 删除后摘要重建／合并顺序的确定性记录（见第 6 节）；
- 缺席检查所含层级的声明：本回执覆盖存储层、输出层、遍历层中的哪几层（见下文验证要求）；不含遍历层时须显式写明；
- 事务最终状态；
- 回执结论：verified 或 failed；
- 签发时间戳。

**签名方式。** 工程上沿用 Merkle 树加 Ed25519 签名的做法：把上述字段组织为规范化载荷，计算 Merkle 根，用 Ed25519 私钥签名。验证方凭签名与 Merkle 根即可校验回执未被篡改，且校验过程不需要接触已删除的原文内容；回执中只出现哈希，不出现被删旧值的明文。

**签名载荷序列化格式（定版，2026-10-30）。** 签名载荷的序列化格式定版为 canonical JSON，即键排序、紧凑分隔符的稳定序列化，不再留作未决项。同一载荷在任何实现中须序列化为完全相同的字节序列，签名与验签均以该字节序列为输入。

注：据 2026-10-30 对 LETHE 官方仓库（github.com/deeplethe/lethe，HEAD b6053b7）的逐行代码核查，其 `receipt.py` 实现签的正是 canonical JSON 载荷，而其仓库版论文 §5.4 写的是 CBOR，两者不一致。本规格以代码为准采用 canonical JSON，并拟在论文相关工作中如实注明这一出入。

**与 LETHE 的语义区别。** LETHE 的回执证明的是删除事件真实发生，即哪些行被删、删除前文本的哈希与日志完整性。本回执证明的是删除效果经过验证：探针集在删除前已经承诺锁定，探针逐项结果与兄弟保全结果被签入回执，且回执结论是探针结果的函数。具体规则为：探针门全过才签 verified；探针门不过且达到轮次上限时签 failed，且该事务不提交。同一事务不得同时存在 verified 与 failed 两张有效回执；事务回滚后重开时，回执以新事务标识重新签发，旧回执标记作废并保留作废记录。

论文写作中不得宣称“首个删除回执”。可宣称的只是回执语义的差别：本回执把预承诺探针的成绩单作为签名的核心内容。

**必引定位：VeriForgot（2026-10-30 补入）。** VeriForgot 验证的是参数级遗忘（MIA+ZK 规格，Preprints.org，非同行评审），与我方行为级探针成绩单不冲突。本规格仅借其预承诺哈希字段，不借其单阈值门与区块链。

**验证要求（据 LETHE 代码核查补入，2026-10-30）。** 据同一核查，LETHE 的 `verify_receipt` 即使带数据库验证，也只重算事件日志 Merkle 根与验签，不检查被删行是否真的已不在库中，更不做行为可恢复性验证。据此，本回执的验证须同时包含以下两项，缺一不可：（一）被删行缺席检查——按回执中的行标识与文本哈希在当前库中查无此行／此哈希，具体分层见下；（二）探针复查——按回执中预承诺的探针集复查目标信息不可恢复、且兄弟保全探针仍通过；兄弟保全复查须在删除后摘要重建完成的状态上运行（见第 6 节）。只通过 Merkle 根重算与验签、不做上述两项的，不算完成本回执的验证。

**被删行缺席检查分三层定义（2026-10-30 补读 TSD-AUDIT 后定版）。**

- 存储层：被删行／向量不在库中——按行标识与文本哈希在事实层、向量层、摘要层查无此行／此哈希。
- 输出层：回答不含目标——经读路径的回答中不出现目标值及其等价表述，由探针复查承载。
- 遍历层：检索打分从未给已删向量计分——对齐 TSD-AUDIT 的 no-intersection 断言，即检索遍历实际计分的向量集合与已删向量集合无交集。

我方若不用 ANN 遍历，则回执与论文中须写明缺席检查不含遍历层，只含存储层与输出层；不得含糊宣称三层全覆盖。只有实际实现并检查了遍历的系统，才可声明含遍历层。

**验收标准。**

- 任一已提交事务都有一张字段完整的 verified 回执，校验签名通过。
- 任一 failed 事务只有 failed 回执，且不存在对应的 verified 回执。
- 回执全文不含被删旧值明文，只含哈希与标识。

## 10. 基准接入规格

### 10.1 BEMULA 适配器

ProvPurge 通过 BEMULA 官方的 MemoryAdapter 接口接入评测，须实现三个方法：

- `reset()`：清空全部记忆状态，包括三层存储、来源图与墓碑表，回到空系统。不得保留上一个实例的任何数据。
- `observe(turn)`：把一轮对话交给系统处理。内部依次走触发识别与写入路径或删除事务。本方法是有写操作的唯一入口。
- `query(question) -> str`：回答一个问题，只走读路径，返回答案字符串。

`query` 绝不写回：回答过程中产生的任何内容不得写入三层存储、来源图或墓碑表。该约束与 BEMULA 官方配置中探针不写回（probe_writeback 为 false）的设定一致，实现中须以断言或等价检查保证，评测期间一旦触发写回即视为接入违规，本实例结果作废。

此外，BEMULA 官方对接入系统有统一的服务条件处理，包括关闭思考与放宽输出长度预算。ProvPurge 接入时接受同样的服务条件，不单独申请特殊设置。

### 10.2 数据访问白名单

评测数据中，系统只允许读取以下字段：说话人（speaker）、文本（text）、时间戳（timestamp）。以下标注字段一律禁用，不得读取、不得间接推断后使用，也不得出现在日志中作为决策依据：事实关联类标注（如 linked_fact_ids）、目标事实类标注（如 target_fact_ids），以及任何能直接指出应删对象或正确答案的标注字段。实现上，数据加载层只把白名单字段传给系统组件，标注字段在加载层即被丢弃，从结构上杜绝误用。

### 10.3 MemCut 辅证 harness

MemCut 的官方代码未公开，辅证 harness 按其论文公布的协议规格自研复刻，要点如下：

- 只复刻其 residual 直喂协议：删除完成后，把溯源到目标及其证据的存活记忆对象绕过检索直接喂给同一骨干模型提问，统计目标信息被恢复的比例，作为残余恢复的辅证指标。
- 不同时复刻其全部基线与全量数据构造；辅证只检验 ProvPurge 与主要基线在该协议下的残余恢复差异。
- 子集规模在试跑阶段确定，确定后写入实验配置并冻结，报告时注明子集的构造方式与规模。
- 报告中明示该 harness 为按论文规格的自研复刻，与官方实现可能存在差异，结论只作辅证使用。

### 10.4 已知坑

以下四项均为已核实的事实，实现与实验设计必须显式规避：

- BEMULA 基线注册表中登记的 memoryos 基线，其实现文件在官方仓库中缺失，选用必报错。复现时跳过该基线，并在论文中如实注明缺失与跳过处理。
- BEMULA 的 Lite 集是全量集的子集：在 Lite 上调参再报告全量结果构成调参泄漏，禁止。任何参数不得在 Lite 或全量评测集上调。
- BEMULA 的 quick_check 只含一个 tiny 合成实例，只用于验证管道连通性，不得用于调参，也不得报告为评测结果。
- 调参一律使用自生成开发集：开发集与评测集在实例层面不重叠，构造方式、规模与种子在实验配置中记录。

另须注意：BEMULA 的 LangMem 适配器特意打开了原厂默认关闭的删除开关，且其删除范围限于当前批次检索到的少量笔记。复现该基线时保持官方适配器行为不变，并在相关工作中说明这一结构上限。

**引用注记：PolyGraph（2026-10-30 更新）。** PolyGraph 的仓库地址于 2026-10-30 复查仍为 404、公开不可达，与 2026-10-29 的核查一致；引用时按公开不可达处理，不宣称已核其代码。

**验收标准。**

- 数据加载层的输出中不含任何禁用标注字段，可由字段清单自动检查。
- `query` 执行期间三层存储与来源图的写计数为零，有日志为据。
